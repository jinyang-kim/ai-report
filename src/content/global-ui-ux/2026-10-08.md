## 접근성: 자동 검사로 잡히는 것조차 나아지지 않았다

WebAIM Million 2026 에 따르면 상위 100만 홈페이지의 95.9%에서 자동 검사로 감지되는 WCAG 2 실패가 나왔고, 이는 2025년 94.8%보다 높다. 페이지당 평균 오류도 51개에서 56.1개로 늘었다. 평균 홈페이지의 요소 수는 1,437개로 1년 새 22.5% 늘었다. [출처: Priority Pixels 요약](https://prioritypixels.co.uk/insights/web-accessibility-is-getting-worse-according-to-the-2026-webaim-million-report/)

| 오류 유형 | 해당 페이지 비율 |
| --- | --- |
| 저대비 텍스트 | 83.9% |
| 대체 텍스트 누락 | 53.1% |
| 폼 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

위 여섯 유형이 검출 오류의 약 96%를 차지하며 7년째 같은 목록이다. [Priority Pixels](https://prioritypixels.co.uk/insights/web-accessibility-is-getting-worse-according-to-the-2026-webaim-million-report/)

**해석상의 한계:** 자동 검사는 WCAG 문제의 일부만 잡으므로 실제 실패율은 더 높을 가능성이 크다. 반대로 95.9%라는 수치가 전년 대비 소폭 오른 것은 통계적 변동 범위일 수 있다는 지적도 있어, "악화"로 단정하기는 이르다. 같은 요약에서 정부 사이트는 평균 42.4개로 전체 평균보다 약 24% 적었다.

## 성능: 통과율은 55%대에서 정체

Chrome UX Report 2026년 8월 릴리스(9월 8일 게시) 기준 CWV 전체를 통과한 origin 은 55.6%(전월 대비 0.2%p 하락)다. 지표별로는 LCP 68.1%, CLS 81.5%, INP 85.3%가 양호했다. [Chrome UX Report release notes](https://developer.chrome.com/docs/crux/release-notes)

세 지표 중 LCP 가 가장 낮아, 통과율을 올리려면 이미지·서버 응답 등 로딩 최적화가 여전히 우선순위다. INP 는 비교적 양호하지만 0.5%p 내려갔다. 이 수치는 origin 단위의 28일 필드 데이터(p75)이므로, 페이지 단위나 사이트 단위 통계와 직접 비교하면 안 된다.

## 기술 표준: WCAG 3.0 은 아직 초안

W3C 는 2026년 3월 3일 WCAG 3 작업 초안을 공개 검토용으로 냈다. [W3C WAI 뉴스](https://www.w3.org/WAI/news/2026-03-03/wcag3) 문서 자체가 초안이며 언제든 변경·대체될 수 있다고 명시한다. [W3C WCAG 3.0 Working Draft](https://www.w3.org/TR/2026/WD-wcag-3.0-20260303/) 따라서 컴플라이언스 기준은 계속 WCAG 2.2 로 두는 것이 안전하다. 확정 시점에 대해서는 출처마다 전망이 달라 여기서는 단정하지 않는다.

## 오늘 바로 적용할 것

- 위 여섯 대표 오류를 자체 사이트에서 먼저 점검한다: 텍스트 대비, 이미지 `alt`, 폼 `label`, 링크·버튼의 접근 가능한 이름, `<html lang>`.
- 자동 검사 통과를 접근성 완료로 보지 말고, 키보드 탐색과 스크린리더 수동 점검을 릴리스 체크리스트에 넣는다.
- CrUX 에서 자사 origin 의 LCP 부터 확인한다. 가장 많은 사이트가 탈락하는 지표다.
- WCAG 3.0 대응은 모니터링만 하고, 현 시점의 설계·감사 기준은 WCAG 2.2 를 유지한다.
