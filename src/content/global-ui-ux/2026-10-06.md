## 접근성

[WebAIM Million 2026](https://webaim.org/projects/million/)은 상위 100만 홈페이지에서 페이지당 평균 56.1개의 오류를 탐지했습니다. 2025년의 51개보다 10.1% 늘었고, WCAG 2 실패가 탐지된 페이지 비율도 94.8%에서 95.9%로 올라 몇 해간 이어진 완만한 개선이 뒤집혔습니다.

| 오류 유형 | 해당 페이지 비율 |
| --- | --- |
| 낮은 대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

위 여섯 유형이 전체 탐지 오류의 96%를 차지합니다([WebAIM](https://webaim.org/projects/million/)). 즉 소수의 반복 패턴만 고쳐도 효과가 큽니다. 레이블 없는 입력창이나 빈 버튼은 스크린리더 사용자가 기능 자체를 쓰지 못하는 실제 장벽이고, 규제 환경에서는 컴플라이언스 리스크가 됩니다.

ARIA 사용도 눈여겨볼 만합니다. 페이지당 ARIA 속성이 평균 133개 이상으로 1년 새 27% 늘었는데, ARIA가 있는 페이지의 평균 오류는 59.1개로 없는 페이지(42개)보다 많았습니다([WebAIM](https://webaim.org/projects/million/)). 다만 이는 상관관계입니다. 복잡한 페이지일수록 ARIA도 오류도 많아지는 면이 있어, ARIA 자체가 오류를 만든다고 단정할 수는 없습니다.

**한계**: WebAIM은 "탐지된 오류가 없다고 해서 접근 가능하거나 적합한 페이지라는 뜻은 아니다"라고 밝힙니다([WebAIM](https://webaim.org/projects/million/)). 자동 검사는 홈페이지 한 장만 보며, 키보드 흐름이나 의미 있는 대체 텍스트 같은 항목은 잡지 못합니다.

## 성능

[2026년 5월 CrUX 기준](https://www.digitalapplied.com/blog/core-web-vitals-benchmarks-2026-pass-rate-reference) 세 지표를 모두 통과한 오리진은 55.9%로, 전월보다 0.8%p 낮아졌습니다. 기준은 75퍼센타일에서 LCP ≤ 2,500ms, INP ≤ 200ms, CLS ≤ 0.1입니다.

- 기기별 통과율: 데스크톱 56%, 모바일 48%로 8%p 차이가 납니다([출처](https://www.digitalapplied.com/blog/core-web-vitals-benchmarks-2026-pass-rate-reference)).
- 모바일 지표별 "Good" 비율: LCP 62%, INP 77%, CLS 81%. 가장 어려운 지표는 응답성이 아니라 로딩(LCP)입니다.
- 플랫폼 편차가 큽니다. Duda 84.87%, Shopify 75.22%, WordPress 46.28%로 약 38%p 벌어집니다.

순위에는 실사용자 필드 데이터(CrUX, 28일 롤링 윈도우)가 쓰이고 Lighthouse 같은 랩 점수는 쓰이지 않습니다. 그래서 랩 점수가 만점이어도 필드 통과를 보장하지 않으며, 개선 효과가 반영되기까지 약 28일이 걸립니다([출처](https://www.digitalapplied.com/blog/core-web-vitals-benchmarks-2026-pass-rate-reference)). 이 수치는 2차 정리 자료에서 가져온 것이므로 원 데이터(CrUX)와 대조해 쓰는 편이 안전합니다.

## 기술 표준

[WCAG 3.0 최신 작업 초안은 2026년 3월 3일자](https://www.adacompliancepros.com/blog/wcag-3-draft-status-procurement)로 2021년 1월 이후 9번째입니다. 이 초안은 섹션별 성숙도 라벨을 도입했지만 181개 조항이 모두 "Developing"에 머물러 있습니다. Bronze·Silver·Gold 적합성 모델도 가장 덜 확정된 "Exploratory" 상태입니다.

- 대비 알고리즘 명세, 대규모 사이트 샘플링 방법 등이 아직 미정입니다.
- 후보 권고안(CR) 일정은 확정되지 않았고, 위키상 전망은 2027년 4분기이나 부정확할 수 있다는 단서가 붙어 있습니다.
- 미국 규제기관 중 WCAG 3.0을 채택한 곳은 없으며, DOJ는 변동하는 표준을 편입하지 않겠다는 입장입니다.

참고로 일부 2차 자료는 2026년 9월에 새 초안이 나왔다고 쓰지만, 이번 조사에서 W3C 1차 자료로 확인하지 못해 본문에는 반영하지 않았습니다.

> 지금 계약과 감사의 기준은 여전히 WCAG 2.x이며, 버전을 명시하는 쪽이 안전합니다.

## 오늘 바로 적용할 것

1. **상위 6개 오류부터 점검**: 저장소 전체에서 레이블 없는 `input`, 텍스트 없는 `button`·`a`, `<html lang>` 누락, `alt` 누락을 검색해 일괄 수정합니다.
2. **대비 검사를 CI에 넣기**: 대비 부족이 83.9%의 페이지에 있습니다. 색 토큰 단위로 임계값(본문 4.5:1)을 자동 검증하세요.
3. **자동 검사 뒤 수동 확인**: 키보드만으로 핵심 흐름을 끝까지 통과하는지, 스크린리더로 폼과 버튼이 읽히는지 확인합니다.
4. **ARIA는 네이티브 요소로 대체 가능한지 먼저 판단**: 네이티브 `button`·`details` 등으로 해결되면 ARIA를 덧붙이지 않습니다.
5. **LCP 우선 점검**: 모바일에서 가장 약한 지표입니다. 필드 데이터(CrUX)로 확인하고 개선 후 28일 윈도우를 감안해 평가합니다.
6. **계약·정책 문서에 "WCAG 2.2 AA"처럼 버전을 명시**합니다.
