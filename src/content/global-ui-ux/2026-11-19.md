## 접근성: 자동 검사로 잡히는 오류조차 늘었다

2026년 2월 스캔 기준 [WebAIM Million](https://webaim.org/projects/million/)은 상위 100만 개 홈페이지의 **95.9%**에서 자동 검출 가능한 WCAG 2 실패를 찾았다(2025년 94.8%). 페이지당 평균 오류는 **56.1개**로 전년 51개에서 늘었다.

| 오류 유형 | 영향 받은 홈페이지 비율 |
| --- | --- |
| 낮은 대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 입력 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

이 여섯 유형이 검출 오류의 96%를 차지한다([WebAIM](https://webaim.org/projects/million/)). 같은 보고서에서 ARIA 를 쓴 페이지는 평균 59.1개, 쓰지 않은 페이지는 42개의 오류를 보였다. 다만 복잡한 페이지일수록 ARIA 도 많이 쓰므로 ARIA 가 원인이라고 단정할 수는 없다.

**한계**: 자동 검사만 센 수치이므로 실제 완전 적합 비율은 4.1%보다 낮을 가능성이 높다([WebAIM](https://webaim.org/projects/million/)). 또 홈페이지만 대상이라 로그인 이후 화면이나 결제 흐름은 반영하지 못한다.

## 성능: INP 는 대체로 양호, 전체 통과는 절반 남짓

[CrUX 릴리스 노트](https://developer.chrome.com/docs/crux/release-notes)에 따르면 최신 데이터셋(2026년 10월, 11월 11일 공개)에서 양호한 INP 를 가진 origin 은 **85.2%**, 코어 웹 바이탈 전체를 통과한 origin 은 **56.3%** 였다. 직전 9월 데이터는 각각 85.4%, 55.9%였다.

INP 는 비교적 잘 통과하는 반면 전체 통과율이 56%대에 머무는 것은 LCP 등 다른 지표가 병목이라는 뜻이다. 이 글에서 확인한 자료에는 지표별 세부 수치가 없어 어느 지표가 주된 원인인지는 단정하지 않는다. CrUX 는 Chrome 사용자의 필드 데이터에 기반한 origin 단위 집계라, 개별 페이지나 다른 브라우저 사용자의 경험과는 다를 수 있다.

## 기술 표준: WCAG 3.0 은 아직 초안

W3C 는 2026년 3월 3일 [WCAG 3 작업 초안 갱신본의 검토를 요청](https://www.w3.org/WAI/news/2026-03-03/wcag3)했고, 의견은 공개 메일링 리스트나 GitHub 로 받는다. 초안 단계이므로 감사·계약·규제 대응의 기준은 계속 WCAG 2.2 로 두는 것이 안전하다. 확정 시점에 대한 공식 일정은 이 글에서 확인하지 못했다.

## 오늘 바로 적용할 것

- 색 대비 점검을 디자인 토큰 단위로 자동화한다. 가장 흔한 오류(83.9%)가 대비 문제다.
- 아이콘 전용 링크·버튼에 접근 가능한 이름(`aria-label` 또는 숨김 텍스트)이 있는지 확인한다. 빈 링크와 빈 버튼은 합쳐 절반 가까운 페이지에서 나타난다.
- 모든 폼 입력에 `<label>` 을 연결하고 `<html lang>` 을 지정한다.
- 자체 CrUX 데이터를 보고 LCP·INP·CLS 중 실제로 통과하지 못하는 지표부터 고친다.
- 자동 검사 통과를 접근성 완료로 보지 말고, 키보드 탐색과 스크린리더 수동 점검을 릴리스 체크리스트에 넣는다.
