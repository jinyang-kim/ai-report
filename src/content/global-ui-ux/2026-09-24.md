## 접근성 — 캐러셀에도 표준 ARIA 패턴이 생겼다

[Chrome 154 베타(9월 2일 진입)](https://developer.chrome.com/blog/chrome-154-beta)는 `::scroll-marker-group` CSS 의사 요소에 **두 가지 모드**를 추가했습니다. 기본값인 링크 모드는 `::scroll-marker-group` 이 `navigation` 역할을, 각 `::scroll-marker` 가 `link` 역할을 갖도록 해 스크롤 구간을 목차처럼 다루고, 새로 추가된 탭 모드는 캐러셀에 맞춰 `tablist` 패턴을 적용해 비활성 탭의 콘텐츠를 접근성 트리에서 숨깁니다. 지금까지 캐러셀·스크롤 스냅 UI 는 개발자가 직접 ARIA 속성을 붙여야 스크린리더가 제대로 읽었는데, 브라우저가 표준 패턴을 기본 제공하면서 구현 편차가 줄어들 전망입니다.

같은 릴리스는 팝오버·다이얼로그의 **라이트 디스미스(가볍게 닫기)** 동작도 다듬어, 스크롤 제스처나 우클릭처럼 사용자가 닫을 의도가 없던 조작으로 열려 있던 패널이 갑자기 사라지는 문제를 막았습니다. 두 변경 모두 지금 당장 코드를 손댈 필요는 없지만, 커스텀 캐러셀에 수동으로 ARIA 를 붙여왔다면 브라우저 네이티브 지원으로 전환할 기회입니다.

## 성능 — DevTools, 소프트 내비게이션 전 구간을 드디어 측정한다

[Chrome DevTools 10월호 업데이트(9월 22일 공개)](https://developer.chrome.com/blog/new-in-devtools-october-2026)의 핵심은 퍼포먼스 패널의 **인사이트(Insights)** 가 소프트 내비게이션을 **처음부터 끝까지 end-to-end 로 측정**하게 됐다는 점입니다. 지금까지는 SPA(싱글 페이지 앱)에서 URL 이 바뀌는 전환처럼 실제 페이지 이동 없이 콘텐츠만 갱신되는 소프트 내비게이션을 CrUX·Lighthouse 계열 도구가 온전히 잡아내지 못한다는 지적이 꾸준했는데, DevTools 쪽에서 먼저 측정 공백을 메운 셈입니다. 아울러 **CPU 성능 티어 오버라이드**를 Chrome DevTools Protocol 로 노출해, 저사양 기기 성능을 흉내 낸 재현 가능한 테스트를 스크립트로 짤 수 있게 됐습니다.

이 밖에 플레임 차트에서 확장 프로그램 트랙을 검색어로 찾는 기능, WebAssembly 스레드 같은 백그라운드 실행을 시각화하는 CPU 프로파일 스레드 뷰도 추가됐습니다. SPA·라우터 기반 사이트를 운영한다면, 실사용자 데이터(CrUX)에는 아직 안 잡히는 소프트 내비게이션 성능 문제를 로컬 DevTools 로 먼저 진단할 수 있습니다.

## 디자인 트렌드 — 계정·셀프서비스 UX, 패스키와 라벨 없는 반품이 기본값 되다

[Baymard Institute 가 9월 9일 공개한 계정·셀프서비스 UX 리서치](https://baymard.com/research-articles/accounts-and-self-service-ux-research-2026)는 4,000시간 이상의 정성 테스트, 1,400개 이상의 UX 이슈, 1,000명 이상 대상 정량 설문을 결합한 결과물로, 2018년 이후 처음 나온 대규모 갱신이자 처음으로 모바일 관찰을 포함했습니다. 계정 보안·로그인 영역에서는 참가자의 **81%가 자주 방문하는 사이트에 카드 정보를 저장**하고 있었고, **60%는 2단계 인증(2FA) 제공을 긍정적으로 평가**했습니다. 전통적인 아이디·비밀번호 조합은 패스키와 일회용 비밀번호로 대체되는 흐름이 뚜렷하며, 비밀번호 요구사항을 입력 중 확인할 수 없거나 마스킹된 비밀번호를 다시 볼 수 없는 등의 문제가 여전히 흔했습니다.

주문 관리에서는 **주문 추적이 가장 중요한 셀프서비스 기능**으로 꼽혔는데, 정작 예상 배송일·배송사명·배송 진행 단계 같은 핵심 정보가 이커머스 사이트 자체에는 빠져 있고 배송사 사이트에서만 확인 가능한 경우가 잦았습니다. 기본 주문 정보를 접힌 섹션에 숨겨두는 것도 아예 표시하지 않는 것과 비슷한 수준으로 나쁜 경험으로 나타났습니다. 반품 프로세스는 2018년 조사 이후 크게 달라져, **라벨 없는 드롭오프와 픽업 서비스**가 마찰을 크게 줄였지만, 반품 가능 여부를 찾기 어렵거나 반품 시작 버튼이 불분명하거나 환불 수단 선택이 헷갈리는 문제는 여전히 주요 장애물로 남아 있습니다.

> "반품 가능 여부와 환불 수단이 불분명하면, 라벨이 없어졌다는 사실 자체는 사용자 경험을 구해주지 못합니다."

## 기술 표준 — 컨테이너 쿼리, 알면서도 안 쓰는 사람이 더 많다

[Smashing Magazine(9월 16일, Victor Ayomipo)](https://www.smashingmagazine.com/2026/09/stop-treating-css-container-queries-traditional-media-queries/)는 컨테이너 쿼리가 이제 주요 브라우저에서 **94% 지원율**을 확보했는데도, State of CSS 2025 설문 기준 개발자의 86%가 존재를 알면서 **실제로 쓰는 비율은 41.4%에 그친다**고 지적합니다. 원인으로는 컨테이너 쿼리가 미디어 쿼리와 문법이 비슷해 같은 용도로 오해하기 쉽다는 점을 꼽습니다. 미디어 쿼리는 뷰포트라는 '바깥'을 보고 내비게이션·헤더·푸터 같은 **페이지 단위(매크로) 레이아웃**을 결정하는 도구인 반면, 컨테이너 쿼리는 컴포넌트 자신의 가용 공간이라는 '안쪽'을 보고 카드·위젯·폼처럼 **여러 레이아웃 맥락에 재사용되는 컴포넌트 단위(마이크로) 레이아웃**을 다루는 도구라는 것이 핵심 구분입니다.

현대 웹에 **2,300개가 넘는 고유 뷰포트 크기**가 존재한다는 점을 감안하면, 임의로 정한 뷰포트 폭 기준 브레이크포인트보다 컴포넌트가 실제로 놓인 공간을 기준으로 삼는 레이아웃 로직이 재사용성 면에서 유리합니다. 다만 컨테이너 쿼리는 부모-자식 관계가 필요하고 커스텀 속성을 쿼리하거나 자기 자신을 참조할 수 없다는 제약이 있어, 페이지 레벨 레이아웃·시스템 색상 설정(다크 모드 등)·기기 성능처럼 뷰포트에 묶인 조건에는 여전히 미디어 쿼리를 써야 합니다. [Chrome 은 9월부터 릴리스 주기를 4주에서 2주로 단축](https://developer.chrome.com/blog/chrome-two-week-release)해 이런 CSS 신기능이 실무 안전권에 들어오는 속도 자체도 빨라지고 있습니다.

## 오늘 바로 적용할 것

1. **커스텀 캐러셀·스크롤 스냅 UI 에 수동으로 ARIA 를 붙여왔다면, Chrome 154 의 `::scroll-marker-group` 탭 모드로 교체를 검토하세요.** 비활성 탭 콘텐츠를 접근성 트리에서 자동으로 숨겨주는 표준 패턴이라 유지보수 부담이 줄어듭니다.
2. **SPA·라우터 기반 서비스는 DevTools 퍼포먼스 패널의 새 소프트 내비게이션 인사이트로 실사용자 데이터에 안 잡히던 전환 성능부터 진단하세요.** CPU 티어 오버라이드로 저사양 기기 재현 테스트도 스크립트화할 수 있습니다.
3. **재사용되는 카드·위젯·폼 컴포넌트의 반응형 처리는 미디어 쿼리 대신 컨테이너 쿼리로 옮기는 것을 검토하세요.** 실사용률이 41.4%에 그친다는 것은 브라우저 지원(94%)에 비해 여전히 저평가된 도구라는 뜻입니다. 페이지 단위 레이아웃과 다크 모드 같은 시스템 설정에는 미디어 쿼리를 그대로 두세요.
4. **계정·주문 페이지가 있다면 배송사명·예상 배송일 같은 핵심 배송 정보를 접힌 섹션 밖으로 꺼내고, 반품 가능 여부와 환불 수단을 첫 화면에서 명확히 보여주세요.** Baymard 리서치에서 반복적으로 지적된 저비용·고효과 개선 지점입니다.
