## 접근성

[WebAIM Million](https://webaim.org/projects/million/) 2026 보고서(2026년 2월 수집, 3월 30일 갱신)에 따르면 상위 100만 홈페이지의 **95.9%** 에서 자동 검출 가능한 WCAG 2 위반이 나왔다. 전년 94.8% 에서 오히려 늘었다. 페이지당 평균 오류도 약 51개에서 **56.1개** 로 약 10% 증가했다.

| 오류 유형 | 영향받은 홈페이지 비율 |
| --- | --- |
| 낮은 텍스트 대비 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 입력 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

출처: [WebAIM Million](https://webaim.org/projects/million/)

주목할 점은 ARIA 다. 페이지당 ARIA 속성은 평균 133개 이상으로 1년 새 27% 늘었지만, ARIA 를 쓴 페이지의 평균 오류는 59.1개로 쓰지 않은 페이지(42.0개)보다 많았다 ([WebAIM Million](https://webaim.org/projects/million/)). 이 수치는 상관관계일 뿐이다. 복잡한 페이지일수록 ARIA 를 더 쓰는 경향이 있어 ARIA 가 오류를 만든다고 단정할 수는 없다.

**한계**: 이 조사는 자동 검사로 잡히는 오류만 센다. 키보드 조작성, 스크린리더에서의 실제 흐름, 맥락에 맞는 대체 텍스트 품질 등은 측정하지 못하므로 실제 접근성 문제는 이보다 많다고 봐야 한다. 대상도 홈페이지에 한정된다.

## 성능

[web.dev](https://web.dev/articles/vitals) 가 안내하는 Core Web Vitals 의 "좋음" 기준은 모바일·데스크톱 각각 **75번째 백분위** 기준으로 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하다. 이번 조사에서 2026년 기준값 변경은 확인하지 못했다. 2026년 변경을 주장하는 블로그가 많았지만 web.dev 에서 뒷받침되지 않았다.

합격률 수치는 출처마다 차이가 커서(대부분 벤더 블로그) 이 리포트에서는 인용하지 않는다. 현황을 보려면 CrUX 대시보드나 Web Almanac 를 직접 확인하는 것이 안전하다.

## 기술 표준

W3C 는 2026년 3월 3일 [WCAG 3 작업 초안(Working Draft)을 검토용으로 공개](https://www.w3.org/WAI/news/2026-03-03/wcag3)했고, 의견은 공개 메일링 리스트나 GitHub 로 받는다. 변경 내역은 WCAG 3 소개 페이지의 "Status: In-progress drafts" 항목에서 확인할 수 있다. 검색 결과에는 9월 초안이 있다는 2차 자료도 있었으나 W3C 공식 페이지에서 직접 확인하지 못해 여기서는 다루지 않는다. 최종 표준까지는 아직 몇 년이 남은 것으로 알려져 있어, 현재 컴플라이언스는 WCAG 2.x 기준으로 대응하는 것이 현실적이다.

## 오늘 바로 적용할 것

- 자사 사이트에서 가장 흔한 세 가지(대비, 대체 텍스트, 폼 레이블)부터 자동 검사로 점검한다. 위 표의 상위 3개가 전체 위반의 대부분을 차지한다.
- ARIA 를 추가하기 전에 네이티브 HTML 요소(`button`, `label`, `a`)로 해결되는지 먼저 본다.
- 자동 검사 통과를 접근성 완료로 간주하지 말고, 핵심 흐름은 키보드와 스크린리더로 직접 확인한다.
- 성능은 평균이 아닌 75번째 백분위의 실사용자 데이터(CrUX)로 LCP·INP·CLS 를 본다.
