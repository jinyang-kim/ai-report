## 접근성 — 유럽은 WCAG 2.2로 상향, 미국은 마감을 다시 늦춘 하루

[유럽위원회 AccessibleEU 센터](https://accessible-eu-centre.ec.europa.eu/content-corner/news/european-accessibility-standard-en-301-549-has-been-updated-2026-09-07_en)에 따르면 유럽 접근성 표준 **EN 301 549 v4.1.1**이 2026년 9월 7일 발표됐습니다. 가장 큰 변화는 웹사이트·소프트웨어·디지털 문서의 기준선을 **WCAG 2.1에서 WCAG 2.2로** 올린 것으로, 새 성공 기준 6개가 추가되고 낡은 4.1.1(파싱) 기준은 삭제됐습니다. 다만 유럽위원회가 관보(Official Journal)에 이 버전을 공식 인용하기 전까지는 현행 **v3.2.1(2021년판)**이 계속 적용되므로 아직 법적 구속력은 없습니다. 그럼에도 문서는 조직이 미리 웹사이트·문서를 WCAG 2.2 기준으로 점검하고 조달 프로세스를 손봐 두라고 권고합니다.

미국은 정반대 방향입니다. [연방관보(Federal Register) 고시](https://www.federalregister.gov/documents/2026/04/20/2026-07663/extension-of-compliance-dates-for-nondiscrimination-on-the-basis-of-disability-accessibility-of-web)에 따르면 법무부(DOJ)는 2026년 4월 20일 주·지방정부 웹·앱 접근성 준수 마감을 1년씩 미뤘습니다 — 인구 5만 이상 기관은 2027년 4월 26일, 5만 미만·특별구는 2028년 4월 26일까지입니다. 기술 기준(WCAG 2.1 Level AA)이나 2024년 최종 규칙의 다른 요건은 그대로이며, 마감 연장이 차별금지 의무 자체를 없애는 것은 아니라서 이 기간에도 민간 소송은 계속될 수 있습니다. 두 사례 모두 "기준은 오르지만 시행은 늦어진다"는 같은 패턴이므로, 지금 프로젝트를 WCAG 2.2 AA에 맞춰 두면 어느 쪽 일정이 당겨져도 손해 볼 일이 없습니다.

## 성능 — Speculation Rules, 모바일 사이트 4곳 중 1곳이 이미 쓴다

[2025 Web Almanac 성능 챕터](https://almanac.httparchive.org/en/2025/performance)는 사전 가져오기·사전 렌더링을 선언적으로 제어하는 **Speculation Rules API**의 채택률을 처음으로 순위 구간별로 집계했습니다. 전체 모바일 사이트의 **25%**가 이미 이 API를 쓰고 있는데, 상위 1,000개 사이트는 5%에 그치는 반면 상위 1,000만 개로 내려가면 25%까지 올라갑니다 — 리포트는 WordPress 기본 탑재가 장기 사이트(long-tail) 채택을 끌어올린 결과로 봅니다. 같은 조사에서 Core Web Vitals 3종을 모두 통과한 사이트는 모바일 48%·데스크톱 56%였고, 모바일 INP 통과율이 2024년 74%에서 77%로 올라 데스크톱과의 격차가 23포인트에서 20포인트로 줄었습니다.

실제 도입 사례도 구체적입니다. [web.dev의 Ray-Ban 케이스 스터디](https://web.dev/case-studies/rayban-speculation-rules)는 데스크톱·모바일에 각기 다른 사전 렌더링 전략을 적용해 **LCP를 4.69초에서 2.66초로(43% 개선)** 줄였고, 그 결과 전환율이 거의 두 배, 이탈률은 13.1%p 감소했다고 밝혔습니다. [Shopify 성능 블로그](https://performance.shopify.com/blogs/blog/faster-storefront-navigations-with-moderate-speculation-rules)는 전체 Liquid 스토어프론트에 `moderate` eagerness 프리페치만 적용해 데스크톱 130ms·모바일 180ms를 모든 백분위·모든 로딩 지표에서 단축했다고 보고합니다. 두 사례 모두 링크 목록을 일일이 관리하지 않고 `href_matches`/`selector_matches` 규칙으로 자동 대상 선정을 한 점이 공통적이라, 별도 서버 인프라 없이도 `<script type="speculationrules">` 한 블록으로 시작할 수 있습니다.

## 디자인 트렌드 — "사용자 = 인간"이라는 전제가 깨졌다

[Nielsen Norman Group의 최신 글](https://www.nngroup.com/articles/ai-agents-as-users/)은 AI 에이전트가 이제 웹사이트·앱의 실질적 사용자라는 전제를 UX 설계에 반영해야 한다고 주장합니다. 에이전트가 인터페이스와 상호작용하는 방식은 세 가지입니다 — 스크린샷을 해석하는 비전 기반(느리고 비효율적), 브라우저의 접근성 트리를 파싱하는 방식(저렴하고 신뢰성 높음), 인터페이스 자체를 우회하는 직접 API 접근입니다. 글은 "명확한 라벨링, 예측 가능한 내비게이션·폼 구조, 시각적 그룹핑이 HTML 구조에도 반영되는 것" 같은 **기존 웹 접근성 원칙이 그대로 에이전트 대응 전략**이 된다고 못박습니다.

> "접근성을 위해 잘 만들어진 인터페이스는 이미 에이전트에게도 더 잘 읽힌다."

다만 모든 서비스가 에이전트 친화적이어야 하는 것은 아니라는 단서도 붙습니다. 광고 수익이 방문 자체에 달린 서비스, 규제·보안이 걸린 금융·의료 서비스, 동적 가격 경쟁력을 지켜야 하는 업종은 에이전트의 직접 접근을 의도적으로 제한할 이유가 있습니다. 접근성 감사를 이미 하고 있는 팀이라면 별도 예산 없이도 에이전트 대응력을 함께 확보하고 있는 셈이니, 감사 항목에 "스크린리더로 가능한 작업을 에이전트도 접근성 트리만으로 완료할 수 있는가"를 추가해 볼 만합니다.

## 기술 표준 — 2026년 Baseline, 보안·압축 API가 실무 안전권에 들어왔다

[web.dev의 Baseline 2026 정리](https://web.dev/baseline/2026)에 따르면 올해 새로 Baseline에 편입된 기능 중 실무 영향이 큰 두 가지는 **Trusted Types**와 **Zstandard(zstd) 콘텐츠 인코딩**입니다. Trusted Types는 `innerHTML` 같은 위험한 DOM 삽입 지점에 일반 문자열 대신 검증된 `TrustedHTML` 객체만 허용해 DOM 기반 XSS를 구조적으로 차단하는 API로, 이제 주요 브라우저 전반에서 크로스브라우저 호환성이 확보됐습니다. Zstandard는 `Accept-Encoding: zstd` 헤더로 협상되는 압축 방식으로, 기존 gzip보다 높은 압축률과 훨씬 빠른 압축 해제 속도를 제공합니다. 이 밖에도 폼 요소 크기를 CSS로 조절하는 `field-sizing`, 컨테이너 스타일 쿼리, `:open` 의사 클래스, 국제화 레이아웃에 쓰이는 `ric` 등 글꼴 상대 단위들이 함께 Baseline에 편입됐습니다.

두 기능 모두 코드 한 줄로 바로 켤 수 있는 종류는 아니지만, Trusted Types는 CSP(Content-Security-Policy) 헤더에 `require-trusted-types-for 'script'`를 추가하는 것으로 점진 도입이 가능하고, Zstandard는 서버·CDN이 이미 지원한다면 별도 클라이언트 작업 없이 협상만으로 전송량을 줄일 수 있습니다. 크로스브라우저 호환성이 이미 확보된 상태이므로, 도입을 미룰 이유는 성능·보안 우선순위 조정뿐입니다.

## 오늘 바로 적용할 것

1. **지금 WCAG 2.2 AA를 기준으로 맞춰 두세요.** 유럽은 EN 301 549 v4.1.1로 기준을 올렸고 미국은 마감만 늦췄을 뿐 WCAG 2.1 AA 요건 자체는 그대로입니다 — 어느 일정이 당겨져도 2.2 AA 기준이면 여유가 있습니다.
2. **접근성 감사 체크리스트에 "에이전트도 접근성 트리만으로 이 작업을 완료할 수 있는가"를 추가하세요.** NN/g 진단대로 명확한 라벨·구조적 마크업이 스크린리더와 AI 에이전트 모두에게 통하는 공통 언어입니다.
3. **핵심 내비게이션 경로에 Speculation Rules를 시범 적용해 보세요.** `moderate` eagerness로 시작하면 Shopify 사례처럼 서버 인프라 변경 없이도 체감 로딩을 단축할 수 있고, Ray-Ban처럼 데스크톱·모바일 전략을 분리하면 효과가 더 커집니다.
4. **CSP에 Trusted Types를 리포트 전용 모드로 먼저 걸어 보세요.** DOM 기반 XSS 취약점을 배포 전에 콘솔 경고로 잡아낼 수 있고, 브라우저 호환성이 이미 Baseline 수준이라 폴백 코드가 따로 필요 없습니다.
