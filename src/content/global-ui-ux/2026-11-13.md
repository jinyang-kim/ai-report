## 접근성

2026년 WebAIM Million 분석(상위 100만 홈페이지)에 따르면 **95.9%의 페이지에서 WCAG 2 A·AA 실패가 자동 감지**됐고, 페이지당 평균 오류는 51개에서 **56.1개**로 늘었다. ([Nexer Digital 분석](https://www.nexerdigital.com/news-and-thoughts/the-webaim-million-report-2026-what-it-tells-us))

| 오류 유형 | 홈페이지 비율 |
| --- | --- |
| 저대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 과반 |
| 폼 라벨 누락 | 51% |
| 빈 링크 · 빈 버튼 · 문서 언어 누락 | 비율 미확인 |

이 여섯 범주가 감지 오류 전체의 약 96%를 차지한다. ([Nexer Digital 분석](https://www.nexerdigital.com/news-and-thoughts/the-webaim-million-report-2026-what-it-tells-us)) 또 ARIA 를 쓰는 페이지는 오류가 더 많았다. 다만 이는 상관관계이며 ARIA 자체가 원인이라는 뜻은 아니다.

**한계**: 이 수치는 자동 검사로 잡히는 오류만 센다. 키보드 동선, 스크린리더 읽기 순서 같은 항목은 자동 도구로 판정할 수 없어 실제 문제는 더 많을 수 있다. 또한 홈페이지만 대상이라 내부 페이지를 대표하지 않는다. 위 수치는 WebAIM 원문이 아닌 2차 분석을 통해 확인했다.

## 성능

2026년 11월 기준 Core Web Vitals 의 세 지표와 임계값은 그대로다. ([Core Web Vitals News, 2026-11](https://blog.mean.ceo/core-web-vitals-news-november-2026/))

- **LCP**: 2.5초 이하 양호, 4초 초과 불량
- **INP**: 200ms 미만 양호, 500ms 초과 불량
- **CLS**: 0.1 미만 양호, 0.25 초과 불량

INP 는 2024년 3월 12일 FID 를 대체했고, 첫 상호작용만 보던 FID 와 달리 방문 전체의 반응성을 본다. 통과하려면 세 지표 모두가 방문의 75퍼센타일에서 양호 구간이어야 하며, 판정은 Lighthouse 같은 랩 데이터가 아니라 실제 Chrome 사용자 현장 데이터로 한다. 메인 스레드의 긴 작업과 무거운 JavaScript 가 INP 불량의 주된 원인이다. ([Core Web Vitals News, 2026-11](https://blog.mean.ceo/core-web-vitals-news-november-2026/))

**한계**: 이 출처는 web.dev 가 아닌 2차 매체다. 임계값은 널리 알려진 값과 일치하지만, 정확한 공식 수치는 web.dev·CrUX 문서로 재확인하는 것이 좋다.

## 기술 표준

W3C WAI 는 2026년 3월 3일 [WCAG 3 작업 초안 갱신을 공지](https://www.w3.org/WAI/news/2026-03-03/wcag3)하며 검토를 요청했다. 초안은 변경될 수 있고 피드백은 메일링 리스트와 GitHub 으로 받는다. 이 초안이 규정 준수 기준이 된 것은 아니므로, 감사와 계약에서는 계속 WCAG 2.x(현재 2.2)를 기준으로 삼는 것이 안전하다. 최종 확정 시기에 대한 2차 출처들의 전망은 엇갈려 여기서는 단정하지 않는다.

## 오늘 바로 적용할 것

1. 가장 흔한 여섯 오류(대비, 대체 텍스트, 폼 라벨, 빈 링크·버튼, `lang` 속성)를 자사 템플릿에서 자동 검사로 먼저 걸러낸다.
2. 자동 검사 통과를 접근성 완료로 보지 말고, 핵심 흐름은 키보드와 스크린리더로 수동 점검한다.
3. 성능은 Lighthouse 점수보다 Search Console·CrUX 의 현장 INP 를 우선 확인하고, 긴 작업을 쪼개 INP 를 줄인다.
4. WCAG 3 는 모니터링만 하고, 준수 목표는 WCAG 2.2 AA 로 유지한다.
