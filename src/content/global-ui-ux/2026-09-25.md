## 접근성 — WCAG 3.0, 이제 A·AA·AAA 대신 '태그+티어'로 간다

[W3C 가 9월 10일 공개한 WCAG 3.0 새 워킹드래프트](https://www.w3.org/WAI/news/2026-09-10/wcag3/)는 적합성 모델을 다시 한번 크게 바꿨습니다. 한때 후보안으로 거론되던 Bronze/Silver/Gold 등급제는 [이번 초안에서 폐기](https://www.w3.org/WAI/standards-guidelines/wcag/wcag3-intro/)됐고, 대신 요구사항을 Core(필수)·Supplemental(추가 개선)·Assertions(정책·절차 문서화)로 나눈 뒤, 각 Core 요구사항에 Physical harm·Risk·Barrier·Friction 이라는 '태그'를 붙이고 전체 준수 수준을 6단계 '티어'로 보고하는 구조를 채택했습니다. Tier 3 가 "모든 Core 요구사항 충족"에 해당하는 최소 적합 기준입니다.

내용 면에서는 [기존 WCAG 2.x 에서 AAA(가장 높은 등급)에만 있던 항목 다수가 Core 로 승격](https://accessibleweb.com/wcag/wcag-3-working-draft-changes/)됐습니다. 자막뿐 아니라 오디오·비디오 콘텐츠의 전체 스크립트 제공, 영상이 보여주지만 말로 설명하지 않는 내용에 대한 음성 설명, 약어가 처음 등장할 때 평문 설명을 붙이는 것(단 "HTML" 처럼 이미 굳어진 표현은 예외)이 대표적입니다. W3C 는 최종 확정까지 수년이 더 걸릴 것으로 보고 있어 당장 준수 라벨을 바꿀 필요는 없지만, Core 로 넘어올 항목은 지금부터 미리 손봐두면 전환 부담이 줄어듭니다.

## 성능 — CrUX 에 광고 지표가 들어왔다, 아직 순위 요인은 아니다

[Chrome 팀이 9월 15일 CrUX(Chrome User Experience Report)에 추가한 4가지 실험적 지표](https://developer.chrome.com/blog/crux-ad-metrics)는 광고가 실사용자 경험에 미치는 부하를 처음으로 공식 수치화합니다. **Ad Count**(뷰포트 내 평균 광고 수), **Ad Density**(뷰포트 면적 중 광고가 차지하는 평균 비율), **Ad Weight: Network**(광고가 소비하는 네트워크 바이트), **Ad Weight: CPU**(광고가 소비하는 CPU 시간, 밀리초 단위)로 구성되며, 모두 실제 크롬 브라우징 세션에서 수집한 데이터입니다.

이 지표들은 CrUX API·CrUX History API·CrUX Vis 에서 바로 조회할 수 있고, 광고가 있는 사이트라면 자사뿐 아니라 타사 사이트도 조회 대상이 됩니다. 다만 Google 은 어떤 지표에도 목표 임계값을 제시하지 않았고, 순위 요인으로 삼겠다는 발표도 없었으며, Core Web Vitals 에도 포함하지 않았습니다. 넷 다 '실험적' 라벨이 붙어 있어 커뮤니티 피드백에 따라 정의가 바뀔 수 있습니다. 광고 지면이 있는 매체·커머스 사이트라면 지금부터 자사 광고 부하를 CrUX 로 모니터링해두는 것이 향후 정식 지표화에 대비하는 방법입니다.

## 디자인 트렌드 — 좋은 프롬프트보다 컨텍스트 큐레이션이다

[Nielsen Norman Group 이 9월 18일 공개한 분석(Tanner Kohler)](https://www.nngroup.com/articles/3-agent-context-roles/)은 AI 에이전트를 능숙하게 쓰는 사용자들이 컨텍스트를 세 역할로 나눠 관리한다고 설명합니다. **글로벌 컨텍스트**는 브랜드 가이드·거버넌스 규칙처럼 상호작용 전반에 걸쳐 거의 변하지 않는 정보이고, **로컬 컨텍스트**는 특정 작업이나 프로젝트에만 적용되는 태스크 목록·프로젝트 기록처럼 파일이나 DB 에 저장돼 AI 가 직접 수정할 수 있는 정보입니다. **앰비언트 컨텍스트**는 이메일·회의 필사본·Slack 메시지처럼 미리 범위를 정하지 않은 원본 스트림으로, 별도 큐레이션 없이 MCP 연결을 통해 실시간으로 접근합니다.

> "좋은 프롬프트를 작성하는 것보다 올바른 컨텍스트를 큐레이션하는 것이 더 중요합니다."

같은 정보가 상황에 따라 여러 역할을 겸할 수 있다는 점, 그리고 컨텍스트가 충분히 준비되어 있으면 프롬프트 자체는 단순해도 에이전트가 효과적으로 작동한다는 점이 실무 시사점입니다. 사내 AI 코파일럿이나 에이전트 기능을 기획한다면, 정보를 저장할 위치와 관리 방식을 이 세 역할에 맞춰 미리 구분해두는 것이 좋습니다.

## 기술 표준 — CSS 만으로 대각선 스크롤과 축별 고정 헤더를

[Microsoft Edge 153(9월 10일 릴리스)](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/release-notes/153)은 스크롤 관련 CSS 속성 두 가지를 새로 선보였습니다. 브라우저는 사용자의 스크롤 제스처가 한쪽 축으로 뚜렷하게 치우치면 그 축에만 스크롤을 '잠그는' 휴리스틱을 기본 적용하는데, 새 `scroll-axis-lock` 속성에 `none` 값을 주면 이 잠금을 끄고 항상 대각선(가로+세로 동시) 스크롤을 허용할 수 있습니다. 지도나 무한 캔버스형 UI 처럼 자유로운 스크롤이 필요한 화면에 바로 적용할 수 있는 옵션입니다.

두 번째는 `overflow` 속성에 `scroll clip` 처럼 두 값을 동시에 지정하는 **단일축 스크롤 컨테이너**입니다. 지금까지 `overflow` 는 한 요소를 가로·세로 모두를 담당하는 스크롤 컨테이너로만 만들 수 있었는데, 이 조합을 쓰면 `position: sticky` 요소가 축마다 다른 스크롤 컨테이너에 종속되도록 만들 수 있어, 열 헤더와 행 헤더를 동시에 고정하는 표 같은 패턴을 JavaScript 없이 CSS 만으로 구현할 수 있습니다. 같은 릴리스에서 미디어 쿼리 `change` 이벤트와 `transitionrun` 이벤트의 발생 시점도 HTML 이벤트 루프 명세에 맞춰 Firefox·Safari 와 순서를 맞췄습니다. 두 스크롤 속성 모두 아직 익스플레이너 단계로 크로스 브라우저 확산은 지켜봐야 합니다.

## 오늘 바로 적용할 것

1. **WCAG 2.x 의 AAA 항목 중 영상 전체 스크립트·음성 설명·약어 평문 설명처럼 이번 초안에서 Core 로 승격된 항목을 지금부터 우선순위에 올리세요.** WCAG 3.0 확정까지는 수년이 걸리지만, 미리 반영해두면 전환 시 부담이 줄어듭니다.
2. **배너·제휴 광고가 있는 사이트를 운영한다면 CrUX API 로 Ad Density·Ad Weight 를 지금부터 모니터링하세요.** 아직 순위 요인은 아니지만, 정식 지표로 굳어지기 전에 자사 광고 부하 실태를 파악해둘 수 있습니다.
3. **사내 AI 에이전트·코파일럿 기능을 설계할 때 정보를 global(거의 불변)·local(작업별)·ambient(원본 스트림) 세 역할로 나눠 저장 위치와 접근 방식을 다르게 설계하세요.** 프롬프트 튜닝보다 컨텍스트 구조화가 에이전트 품질에 더 직접적으로 기여합니다.
4. **자유 스크롤 캔버스나 열·행 헤더를 동시에 고정하는 표가 필요하면 `scroll-axis-lock: none` / `overflow: scroll clip` 를 Edge·Chromium 계열에서 먼저 검토하세요.** 다만 아직 익스플레이너 단계이므로 프로덕션 적용 전 타깃 브라우저 지원 여부를 확인해야 합니다.
