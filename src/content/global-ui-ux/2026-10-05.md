## 접근성: 8년 만에 처음 보이는 뚜렷한 후퇴

2026년 2월 분석 기준으로 WebAIM 은 상위 100만 홈페이지에서 평균 56.1개의 오류를 검출했고, 이는 2025년의 51개보다 10.1% 많습니다. WCAG 2 실패가 감지된 홈페이지 비율도 94.8% 에서 95.9% 로 올랐습니다 ([WebAIM Million 2026](https://webaim.org/projects/million/)). 해마다 조금씩 나아지던 추세가 꺾인 셈입니다.

오류는 소수 유형에 집중됩니다. 상위 6개 유형이 전체 오류의 96% 를 차지합니다 ([WebAIM Million 2026](https://webaim.org/projects/million/)).

| 오류 유형 | 해당 페이지 비율 |
| --- | --- |
| 저대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

복잡도도 같이 커졌습니다. 홈페이지당 평균 요소 수는 1,437개로 1년 사이 14.3% 늘었습니다. ARIA 속성은 페이지당 평균 133개로 27% 늘었는데, ARIA 가 있는 페이지의 평균 오류(59.1개)가 없는 페이지(42개)보다 많았습니다 ([WebAIM Million 2026](https://webaim.org/projects/million/)). 다만 이것은 상관관계입니다. ARIA 가 오류를 만든다는 인과의 증거는 아니고, 복잡한 페이지일수록 ARIA 도 오류도 많아지는 효과가 섞여 있을 수 있습니다.

**한계**: WebAIM 은 자동 검사로 홈페이지만 봅니다. 자동 검사로 잡히지 않는 키보드 흐름, 스크린리더 문맥, 로그인 뒤 화면의 문제는 이 수치에 들어 있지 않으므로 실제 상황은 이보다 나쁠 수 있습니다.

## 성능: 병목은 INP 가 아니라 LCP

2026년 5월 CrUX 데이터에서 Core Web Vitals 3종을 모두 통과한 origin 은 55.9% 입니다. 기준은 실사용자 75번째 백분위에서 LCP ≤ 2.5초, INP ≤ 200ms, CLS ≤ 0.1 이며, 모바일 통과율은 48%, 데스크톱은 56% 로 8%p 차이입니다 ([Core Web Vitals Benchmarks 2026](https://www.digitalapplied.com/blog/core-web-vitals-benchmarks-2026-pass-rate-reference)).

모바일에서 지표별로 보면 LCP 62%, INP 77%, CLS 81% 가 양호 판정이라, 전체 통과를 가장 많이 막는 것은 로딩(LCP)입니다 ([같은 자료](https://www.digitalapplied.com/blog/core-web-vitals-benchmarks-2026-pass-rate-reference)). 플랫폼 격차도 큽니다. Duda 는 84.87%, WordPress 는 46.28% 이며, WordPress 의 INP 통과율은 85.89% 로 약점이 반응성이 아니라 로딩에 있습니다.

2026년 갱신에서는 임계값이 바뀌지 않았고, INP 측정 방식이 더 엄격해졌으며 SPA 를 위한 CrUX 소프트 내비게이션 커버리지가 넓어졌고 PageSpeed Insights 에서 TTFB 가 진단 지표로 더 눈에 띄게 되었다고 합니다 ([MonsterMegs](https://monstermegs.com/blog/core-web-vitals-update/)). 이 부분은 2차 블로그 요약이므로 정확한 변경 내용은 Chrome 의 공식 CrUX 릴리스 노트로 재확인하기를 권합니다.

**한계**: CrUX 는 28일 롤링 필드 데이터라 개선 효과가 늦게 반영되고, 집계 단위가 origin 이라 페이지별 문제는 가려집니다. 위 수치도 2차 자료가 인용한 값입니다.

## 기술 표준: WCAG 3.0 은 아직 초안

W3C 는 2026년 3월에 WCAG 3.0 작업 초안을 갱신했고, 이전 초안의 "outcomes" 가 "requirements" 로 바뀌어 174개가 되었습니다 ([Centre For Accessibility Australia](https://www.accessibility.org.au/new-2026-update-for-the-wcag-3-0-working-draft/)). 적합성 모델은 단일 수준과 그 아래·위의 보고 단계를 두는 방향으로 논의 중입니다. Candidate Recommendation 은 2027년 4분기 무렵, 최종 권고는 2028년 이후로 예상됩니다 ([AccessibleWeb](https://accessibleweb.com/wcag/wcag-3-working-draft-changes/)). 강제력이 있는 기준이 아니며 일정은 바뀔 수 있습니다. 규정 준수 실무는 당분간 WCAG 2.2 AA 를 기준으로 삼는 것이 안전합니다.

> 접근성 오류의 96% 는 여섯 가지 기본 유형에서 나옵니다. 새 표준을 기다리기보다 이 여섯 가지부터 막는 편이 효과가 큽니다.

## 오늘 바로 적용할 것

- **대비 점검**: 본문·메타 텍스트의 대비를 4.5:1 이상으로 확인합니다. 저대비는 전체 페이지의 83.9% 에서 나타난 1위 오류입니다.
- **빈 링크·버튼 제거**: 아이콘 전용 컨트롤에 접근 가능한 이름(텍스트 또는 `aria-label`)이 있는지 검사합니다.
- **폼 레이블·`lang` 속성**: 모든 입력에 `<label>` 을 연결하고 `<html lang>` 을 지정합니다.
- **ARIA 는 최소로**: 네이티브 HTML 요소로 되는 것은 ARIA 를 덧붙이지 않습니다.
- **LCP 우선 점검**: 모바일 LCP 가 2.5초를 넘는지 CrUX 나 PageSpeed Insights 의 필드 데이터로 먼저 확인합니다.
- **자동 검사 + 수동 검사**: 자동 도구는 일부만 잡으므로 키보드 탐색과 스크린리더 확인을 병행합니다.
