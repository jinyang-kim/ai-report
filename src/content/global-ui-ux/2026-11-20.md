## 접근성

[WebAIM Million](https://webaim.org/projects/million/) 2026년판(2026년 2월 스캔)에 따르면 상위 100만 홈페이지 중 **95.9%** 에서 WCAG 2 실패가 감지됐다(전년 94.8%). 페이지당 평균 오류는 **56.1개**로 전년 51개보다 약 10% 늘었다.

| 오류 유형 | 해당 홈페이지 비율 |
| --- | --- |
| 낮은 대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 입력 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

이 여섯 유형이 감지된 전체 오류의 약 96% 를 차지한다([WebAIM](https://webaim.org/projects/million/)). 실제 영향은 분명하다. 대비 부족은 저시력·야외 사용자를, 레이블·대체 텍스트·이름 없는 링크와 버튼은 스크린리더 사용자를 직접 막는다.

ARIA 속성은 페이지당 133개 넘게 감지돼 1년 새 27% 늘었는데, ARIA 가 있는 페이지의 평균 오류는 59.1개로 없는 페이지(42개)보다 많았다([WebAIM](https://webaim.org/projects/million/)). 다만 이는 상관관계일 뿐 ARIA 가 오류를 일으킨다는 인과 증거는 아니다. 또 이 조사는 자동 검사 도구 기반이라 WCAG 위반의 일부만 잡고, 홈페이지만 대상으로 하므로 실제 서비스 전반을 대표하지 않는다.

## 기술 표준

W3C 는 2026년 3월 [WCAG 3 작업 초안 갱신](https://www.w3.org/WAI/news/2026-03-03/wcag3)을 공개하고 의견을 받고 있다. [W3C 문서](https://www.w3.org/TR/WCAG30/)는 이 초안이 미완성이며 최종 요구사항이 달라질 수 있다고 밝힌다. 또한 WCAG 3 이 WCAG 2 를 대체하는 것이 아니며 WCAG 2.2 가 폐기되지 않는다고 설명한다. 따라서 규정 준수 기준은 당분간 WCAG 2.2 로 두는 것이 안전하다. 확정 일정에 관한 수치는 이번 조사에서 W3C 1차 출처로 확인하지 못해 싣지 않는다.

## 성능

[web.dev](https://web.dev/blog/lcp-and-inp-are-now-baseline-newly-available)에 따르면 2025년 12월 12일 Safari 26.2 출시로 LCP 와 INP 가 **Baseline Newly available** 이 됐다. 최신 Chrome·Edge·Firefox·Safari 에서 모두 측정 API 를 쓸 수 있다는 뜻이다. 단, iOS 의 Chrome 은 WebKit 기반이라 CrUX 에 데이터를 보내지 않는다.

CrUX [릴리스 노트](https://developer.chrome.com/docs/crux/release-notes)에는 2026년 5월 데이터 기준으로 Core Web Vitals 를 모두 통과한 origin 이 55.9%(3월 56.4%), INP 통과가 86.6%, LCP 통과가 68.9% 로 기재돼 있다는 검색 결과를 확인했다. 이 수치는 검색 요약을 통한 것이어서 원문 페이지에서 직접 대조하지 못했으니 참고용으로 보는 편이 좋다. 어느 쪽이든 LCP 가 INP 보다 통과율이 낮은 병목이라는 점은 같다.

## 오늘 바로 적용할 것

- 텍스트 대비를 먼저 점검한다: 가장 흔한 오류(83.9%)이고 자동 검사로 쉽게 잡힌다.
- 아이콘 전용 버튼·링크에 접근 가능한 이름(`aria-label` 또는 보이는 텍스트)이 있는지, `<html lang>` 이 있는지 확인한다.
- ARIA 를 추가하기 전에 네이티브 HTML 요소로 해결되는지 먼저 따져 본다.
- 자동 검사 통과를 접근성 완료로 보지 말고 키보드·스크린리더 수동 점검을 병행한다.
- RUM 으로 LCP·INP 를 75퍼센타일 기준으로 측정하되, iOS Chrome 사용자는 CrUX 에 잡히지 않음을 감안한다.
