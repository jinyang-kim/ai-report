## 접근성

[WebAIM Million 2026](https://webaim.org/projects/million/)은 상위 100만 개 홈페이지에서 평균 56.1개의 오류를 찾았습니다. 전년(51개)보다 10.1% 늘어, 완만하게 개선되던 흐름이 뒤집혔습니다.

가장 흔한 실패 유형은 다음과 같습니다([WebAIM](https://webaim.org/projects/million/)).

| 실패 유형 | 홈페이지 비율 |
| --- | --- |
| 저대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 입력 레이블 누락 | 51% |
| 빈 링크 | 46.3% |
| 빈 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

이 여섯 유형이 감지된 오류의 96%를 차지합니다. 저대비 텍스트는 전년 79.1%에서 늘었고 페이지당 약 34건 나타났습니다([WebAIM](https://webaim.org/projects/million/)).

> ARIA를 쓴 페이지는 평균 59.1개, 쓰지 않은 페이지는 42개의 오류가 있었습니다.

ARIA 속성은 페이지당 평균 133개로 1년 새 27% 늘었습니다([WebAIM](https://webaim.org/projects/million/)). 다만 상관관계이지 인과는 아닙니다. 복잡한 페이지일수록 ARIA도 오류도 많아지기 때문입니다. 자동 검사는 감지 가능한 오류만 세므로 실제 스크린리더 사용성은 별도로 확인해야 합니다.

## 성능

Core Web Vitals의 "양호" 기준은 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하이며, 실제 사용자 75번째 백분위수로 판정합니다([RoastWeb](https://roastweb.com/blog/core-web-vitals-explained-2026)). INP는 FID를 대체한 지표로, 첫 상호작용만이 아니라 페이지 생애 전체의 상호작용 지연을 봅니다. 50ms를 넘는 동기 JavaScript 작업은 메인 스레드를 막으므로 긴 작업을 쪼개는 것이 핵심입니다. 이 수치는 2차 해설 자료 기준이라 Google 공식 문서와 함께 확인하는 편이 안전합니다.

## 기술 표준

W3C는 [2026년 9월 10일 WCAG 3 작업 초안](https://www.w3.org/WAI/news/2026-09-10/wcag3/)을 공개하고 의견을 받고 있습니다. 의견은 wai@w3.org 메일링 리스트나 GitHub로 낼 수 있고, 공지에는 마감일이 명시돼 있지 않습니다. 2차 해설에 따르면 적합성 모델이 A/AA/AAA 대신 점수 기반의 Bronze·Silver·Gold로 바뀌고, Candidate Recommendation은 2027년 4분기경, 정식 권고는 2028년 이후로 전망됩니다([WebAbility](https://www.webability.io/blog/wcag-3-0-explained)). 따라서 현재 컴플라이언스의 기준은 여전히 WCAG 2.2입니다.

## 오늘 바로 적용할 것

- 색 대비부터 점검합니다. 가장 흔한 실패이고 디자인 토큰 단위로 한 번에 고칠 수 있습니다(라이트·다크 모두).
- 이미지 `alt`, 폼 `label`, 링크·버튼의 접근 가능한 이름 누락을 CI 자동 검사에 넣습니다.
- ARIA는 네이티브 HTML로 해결되지 않을 때만 씁니다. 기존 ARIA 사용처를 실제 스크린리더로 한 번 검증합니다.
- 100ms 이상 걸리는 이벤트 핸들러를 찾아 긴 작업을 나눕니다(INP 대응).
- WCAG 3 초안은 모니터링만 하고, 계약·규제 대응은 WCAG 2.2 AA를 기준으로 유지합니다.
