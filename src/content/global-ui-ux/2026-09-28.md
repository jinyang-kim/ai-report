## 접근성 — 위젯을 달아도 소송은 막지 못한다

[UsableNet 이 매달 집계하는 ADA 웹 접근성 소송 트래커](https://info.usablenet.com/ada-website-compliance-lawsuit-tracker)에 따르면 2026년 8월 미국에서 432건의 신규 소송이 제기됐습니다. 이 중 108개 기업은 과거에도 디지털 접근성 소송을 겪은 반복 피소 기업이었고, 특히 134개 기업은 소송 당시 이미 제3자 접근성 위젯이나 오버레이 도구를 사이트에 적용 중이었습니다.

위젯을 달아도 소송을 피하지 못한다는 이 수치는 새로운 이야기는 아니지만, 반복해서 확인될수록 시사점이 분명해집니다. 자동 오버레이 스크립트 하나로 컴플라이언스 리스크를 '해결'했다고 간주하는 접근은 실제 법적 노출을 줄이지 못하며, 스크린리더 실사용 테스트와 시맨틱 마크업 같은 근본적인 개선을 대체할 수 없습니다. 전자상거래·요식업처럼 소송 비중이 높은 업종이라면 위젯 도입 여부와 무관하게 핵심 사용자 흐름(결제, 검색, 폼 제출)의 키보드·스크린리더 접근성을 직접 점검해두는 편이 안전합니다.

## 성능 — INP 가 5개월째 나빠지는데, 이유를 아무도 모른다

[Chrome 팀이 발행하는 CrUX(Chrome UX Report) 2026년 8월 릴리스 노트](https://developer.chrome.com/docs/crux/release-notes)는 양호(good) INP(Interaction to Next Paint) 비율이 85.3%로 전월(85.7%) 대비 0.5%포인트 더 떨어졌다고 밝혔습니다. [성능 컨설턴트 Harry Roberts 가 9월 9일 정리한 바에 따르면](https://csswizardry.com/2026/09/web-perf-wednesday-008-good-inp-rates-keep-falling/) 이 수치는 3월 87.2%에서 시작해 5개월 연속 하락한 것이며, Chrome 팀 스스로도 릴리스 노트에 "지속적인 INP 퇴행이 우려스럽지만 명확한 원인은 없다"고 적었습니다.

Roberts 는 이런 전역(global) CrUX 추세가 사이트·브라우저·기기·트래픽 구성 변화 등 여러 요인이 뒤섞인 결과라 특정 제품에서 무엇이 나빠졌는지는 알려주지 않는다고 지적합니다. 원인 불명의 업계 전체 추세를 좇기보다, 각 팀이 보유한 RUM(실사용자 모니터링) 데이터를 경로·상호작용 유형·기기·브라우저 버전별로 세분화해 자사 서비스에서 실제로 느려진 상호작용을 특정하는 것이 더 실질적인 대응이라는 조언입니다.

## 디자인 트렌드 — AI 로 만들었다고 밝힐지, PACED 로 판단하라

[Nielsen Norman Group 이 9월 25일 공개한 Taylor Dykes 의 글](https://www.nngroup.com/articles/disclose-ai-paced/)은 콘텐츠 제작에 AI 를 썼다는 사실을 공개할지 판단하는 **PACED** 프레임워크를 제안합니다. 다섯 요소는 법률·조직·플랫폼 정책이 공개를 요구하는지(**Policy**), 대상 독자가 AI 사용을 어떻게 받아들이는지(**Audience**), 창의성·진정성·개인적 연결처럼 인간 기여가 중요한 맥락인지(**Context**), 사용자가 애초에 공개를 기대하는지(**Expectations**), AI 가 콘텐츠에 얼마나 결정적으로 기여했는지(**Degree of AI use**)입니다.

리서치에서 발견한 역설은 실무에 바로 적용할 만합니다 — 사용자들은 "AI 사용을 공개해달라"고 말하면서도, 막상 공개된 콘텐츠는 더 부정적으로 평가하는 경향을 보입니다. 개인적인 편지나 감정 표현처럼 진정성이 중요한 콘텐츠일수록 부정적 반응이 강했고, 거래성·정보 전달 목적의 콘텐츠에서는 반응이 중립적이었습니다. 사내 AI 라이팅 도구나 챗봇 응답에 공개 배지를 넣을지 고민 중이라면, 일괄 규칙 대신 PACED 다섯 요소로 콘텐츠 유형별 정책을 나눠 적용하는 편이 사용자 신뢰와 콘텐츠 품질 인식 양쪽을 지킬 수 있습니다.

## 기술 표준 — Chrome 이 2주마다 새 버전을, 그리고 클릭 한 번으로 끝나는 카메라 권한을

[Chrome 팀이 발표한 릴리스 주기 변경](https://developer.chrome.com/blog/chrome-two-week-release)에 따라, [9월 8일 출시된 Chrome 153](https://developer.chrome.com/release-notes/153) 부터 안정 버전 배포 주기가 기존 4주에서 2주로 단축됐습니다. 엔터프라이즈 관리자를 위한 Extended Stable 채널은 기존 8주 주기를 그대로 유지하며, 개발자는 안정 버전 출시 3주 전 베타 채널로 변경 사항을 미리 확인할 수 있습니다. 배포 빈도가 늘어난 만큼 릴리스 노트를 더 자주 확인해야 회귀를 조기에 잡을 수 있습니다.

같은 Chrome 153 에는 [카메라·마이크 접근을 위한 선언형 HTML 엘리먼트 `<camera>`·`<microphone>`](https://developer.chrome.com/blog/usermedia-html-element)도 새로 들어왔습니다. 앞서 6월 Chrome 151 에 도입된 `<usermedia>` 엘리먼트의 특화 버전으로, 스크립트가 아닌 사용자의 실제 클릭이 있어야 브라우저가 통제하는 고정 UI 를 통해 권한 요청이 시작됩니다. 기존 `getUserMedia()` 는 필요 이상으로 카메라와 마이크 권한을 한꺼번에 요청하는 경우가 많았는데, 이 엘리먼트들은 용도를 영상 또는 음성 단일 기능으로 좁혀 요청할 수 있게 해 과잉 권한 요청을 줄입니다.

## 오늘 바로 적용할 것

1. **접근성 위젯·오버레이를 이미 쓰고 있어도 안심하지 말고, 결제·검색·폼 제출 같은 핵심 흐름을 실제 스크린리더로 직접 점검하세요.** 위젯 사용 중에도 소송당한 기업이 8월에만 134곳이었습니다.
2. **CrUX 전역 INP 추세를 좇기보다 자사 RUM 데이터를 경로·기기·브라우저 버전별로 나눠 실제로 느려진 상호작용을 찾으세요.** Chrome 조차 원인을 특정하지 못한 전역 지표는 개별 제품 진단에 한계가 있습니다.
3. **AI 로 생성한 콘텐츠의 공개 여부를 정할 때 일괄 규칙 대신 PACED(정책·대상·맥락·기대·AI 기여도) 로 콘텐츠 유형별 정책을 나누세요.** 특히 진정성이 중요한 콘텐츠에서는 공개가 오히려 부정적 평가를 부를 수 있다는 점을 감안해야 합니다.
4. **Chrome 의 2주 릴리스 주기 전환에 맞춰 릴리스 노트 확인 주기를 앞당기고, 카메라·마이크 권한이 필요한 기능은 `<camera>`/`<microphone>` 엘리먼트 도입을 검토하세요.** 불필요하게 넓은 권한 요청을 줄이면 사용자 허용률 개선을 기대할 수 있습니다.
