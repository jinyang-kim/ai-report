## 접근성: 7년 만에 개선 추세가 꺾였다

2026 WebAIM Million 은 상위 100만 개 홈페이지의 95.9%에서 WCAG 2 실패가 자동 탐지됐고, 이는 전년 94.8%보다 높다고 밝혔다. 페이지당 평균 오류도 56.1개로 전년 대비 10.1% 늘었다 ([Priority Pixels](https://prioritypixels.co.uk/insights/web-accessibility-is-getting-worse-according-to-the-2026-webaim-million-report/)).

| 오류 유형 | 해당 홈페이지 비율 |
| --- | --- |
| 저대비 텍스트 | 83.9% |
| 이미지 대체 텍스트 누락 | 53.1% |
| 폼 입력 레이블 누락 | 51% |
| 텍스트 없는 링크 | 46.3% |
| 텍스트 없는 버튼 | 30.6% |
| 문서 언어 누락 | 13.5% |

위 수치는 [WebAIM Million 2026 을 정리한 검색 결과](https://prioritypixels.co.uk/insights/web-accessibility-is-getting-worse-according-to-the-2026-webaim-million-report/) 기준이다. 같은 6가지 유형이 7년 연속 전체 오류의 약 96%를 차지한다. 저대비 텍스트는 전년 79.1%에서 83.9%로 올랐다.

원인으로는 페이지 복잡도 증가가 꼽힌다. 평균 요소 수는 1,437개로 1년 새 22.5% 늘었고 2019년의 거의 두 배다. ARIA 사용은 1년간 27% 늘었는데, ARIA 를 쓴 페이지의 평균 오류는 59.1개로 쓰지 않은 페이지(42개)보다 많았다. 플랫폼별로는 WordPress 52.8개, Shopify 75.1개, Magento 75.8개였다 ([Priority Pixels](https://prioritypixels.co.uk/insights/web-accessibility-is-getting-worse-according-to-the-2026-webaim-million-report/)). 해당 글은 서드파티 프레임워크·라이브러리 의존과 AI 보조 개발을 악화 요인으로 해석하지만, 프레임워크별 분석으로 확인한 것은 아니다.

**한계**: 자동 검사는 WCAG 위반의 일부만 잡는다. 실제 비준수율은 이보다 높을 가능성이 크고, 반대로 오류 0개가 곧 사용 가능함을 뜻하지도 않는다.

## 기술 표준: WCAG 3.0 은 아직 초안

W3C 는 2026년 3월 3일 WCAG 3.0 작업 초안(Working Draft) 갱신본에 대한 의견을 요청했다. 의견은 공개 메일링 리스트(wai@w3.org)나 GitHub 이슈로 받는다 ([W3C WAI](https://www.w3.org/WAI/news/2026-03-03/wcag3)). 문서 자체도 언제든 갱신·대체·폐기될 수 있다고 명시한다 ([W3C WCAG 3.0](https://www.w3.org/TR/wcag30/)).

검색 결과 간 일부 내용(최신 초안 날짜, 가이드라인·조항 개수, 일정)이 엇갈려 여기서는 확인된 3월 갱신 사실만 적는다. 실무에서는 계약·컴플라이언스 기준을 계속 WCAG 2.2 로 두는 것이 안전하다.

## 성능: Core Web Vitals 기준은 그대로

2026년에도 임계값은 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하(75퍼센타일 기준)로 유지된다. INP 는 2024년 3월 FID 를 대체했고, 첫 상호작용만 보던 FID 와 달리 방문 중 모든 상호작용을 평가한다 ([anim.hr](https://anim.hr/en/blog/core-web-vitals-2026)). 이 출처는 SEO 블로그라 2차 자료이며, 이번 조사에서 2026년 10월자 Google 공식 변경 공지는 찾지 못했다. 최신 기준은 web.dev 와 Chrome 개발자 문서에서 직접 확인하자.

## 오늘 바로 적용할 것

- 디자인 토큰의 텍스트 대비를 자동 계산으로 검증한다(일반 텍스트 4.5:1). 가장 흔한 오류를 가장 싸게 막는 방법이다.
- 아이콘 전용 버튼·링크에 접근 가능한 이름이 있는지 점검한다. 각각 30.6%, 46.3%의 홈페이지에서 비어 있었다.
- 폼 입력마다 `label` 을 연결하고 `<html lang>` 을 확인한다.
- ARIA 는 네이티브 요소로 해결되지 않을 때만 쓴다. 쓴 페이지의 오류가 더 많다는 통계가 이를 시사한다(인과는 아님).
- 자동 검사 통과를 목표로 삼지 말고, 키보드·스크린리더 수동 점검을 릴리스 체크리스트에 넣는다.
