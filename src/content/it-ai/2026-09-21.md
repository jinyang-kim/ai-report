## pnpm 12 — 자바스크립트 대신 러스트를 택하다

패키지 매니저 **pnpm** 이 8월 26일 12.0.0을 내놓으며 핵심 엔진을 자바스크립트/TypeScript 에서 러스트로
완전히 갈아엎었습니다. 현재 코드베이스 구성은 러스트 65.9%, TypeScript 33.5% 로, Node.js 를 거쳐
파일시스템을 다루던 오버헤드를 걷어낸 결과입니다
([The Register](https://www.theregister.com/devops/2026/09/04/javascript-installer-pnpm-recast-in-rust-because-ecmascript-cant-keep-up/5294394)).
효과는 수치로도 뚜렷합니다 — 깨끗한 설치가 8.2초에서 5초로, 캐시가 있는 재설치는 472ms 에서 15ms 로
약 31배 빨라졌고, Vercel 이 자사의 대규모 워크스페이스에서 측정한 설치 시간은 64.4～90.5% 줄었습니다
([InfoQ](https://www.infoq.com/news/2026/09/pnpm-12-rust/)).

> It was faster to rewrite pnpm in Rust than to migrate to ESM.

pnpm 유지보수자 Zoltan Kochan 이 남긴 이 말은 재작성의 동기를 압축합니다
([The Register](https://www.theregister.com/devops/2026/09/04/javascript-installer-pnpm-recast-in-rust-because-ecmascript-cant-keep-up/5294394)).
vlt CEO Darcy Clarke 는 이를 두고 "Node 의 개발자 경험이 부족하다는 점을 드러낸 사건"이라고 평했습니다
([InfoQ](https://www.infoq.com/news/2026/09/pnpm-12-rust/)). 다만 명령어·플래그·lockfile 포맷 등 사용자가
보는 워크플로는 pnpm 11 과 동일하게 유지됩니다 — Git 의존성은 정규 HTTPS URL 로 해석되고, Linux 에서는
reflink 보다 하드링크를 먼저 시도하며, `pnpm-workspace.yaml` 의 인식되지 않는 키는 조용히 무시되지 않고
보고됩니다([pnpm 12.0.0 GitHub Releases](https://github.com/pnpm/pnpm/releases/tag/v12.0.0)).

재작성은 출시로 끝나지 않고 pnpm 의 범위 자체를 넓히는 발판이 됐습니다. 9월 8일 12.4는 npm·Python·
Cargo 의존성 관리를 추가했고, 9월 18일 12.5는 Python 인터프리터를 자동으로 고르고 설치해 "Python
환경이 이제 pnpm 스토어 안에 산다"고 표현할 만큼 통합했습니다. `pyproject.toml` · `Cargo.toml` 을
직접 읽고, PyPI 레지스트리를 `ecosystem: pypi` 로 지정할 수 있습니다
([pnpm 12.5.0 GitHub Releases](https://github.com/pnpm/pnpm/releases/tag/v12.5.0)).

### 실무 영향

- 대형 모노레포에서 CI 설치 시간이 병목이었다면 12로 업그레이드만으로도 체감 가능한 단축을 기대할 수
  있습니다. 단 `pnpm install --resolution-only` 가 제거되고 `pnpm peers check` 로 대체됐으므로, 이
  플래그를 쓰는 CI 스크립트가 있다면 먼저 점검해야 합니다.
- Python·Rust 코드가 섞인 폴리글랏 모노레포를 운영 중이라면, 별도 도구 없이 pnpm 하나로 의존성을
  통합 관리하는 방향이 실질적인 선택지가 됐습니다.

## React Compiler 도 러스트로 — 번들러·매니저·컴파일러가 한 방향을 가리키다

React 팀은 6월 9일 React Compiler 를 러스트로 포팅하는 PR `[compiler] Port React Compiler to Rust`
(facebook/react#36173)를 실험적 브랜치로 메인 저장소에 병합했습니다. 상태는 "메타 내부 테스트에
앞서 파트너 피드백을 모으는 작업 진행 중"이며, 기존 TypeScript 버전과 동일한 HIR(고수준 중간 표현)·
제어 흐름 그래프·SSA 아키텍처를 유지한 채 코드 대부분을 AI 가 작성했습니다. 1,725개 fixture 전부를
통과했고 알려진 버그는 없다고 명시돼 있습니다
([facebook/react#36173](https://github.com/facebook/react/pull/36173)).

성능은 Babel 플러그인으로 드롭인 교체했을 때 약 3배, 변환 로직만 떼어놓고 보면 최대 10배 빨라졌고,
러스트로 작성된 번들러 Turbopack 에 네이티브로 연동했을 때는 컴파일 경로가 20～50% 단축됩니다
([facebook/react#36173](https://github.com/facebook/react/pull/36173)).

이 흐름은 갑자기 등장한 게 아닙니다. Vite 는 이미 3월 12일 8.0을 정식 출시하면서 러스트 기반 번들러
Rolldown 을 esbuild·Rollup 이원 구조를 대체하는 단일 번들러로 채택했고, 빌드 속도는 최대 10～30배,
Linear 사의 실사례는 46초에서 6초로 줄었다고 밝혔습니다
([Vite Blog](https://vite.dev/blog/announcing-vite8)). 번들러(Rolldown)·패키지 매니저(pnpm)·컴파일러
(React Compiler)가 반년 사이 차례로 같은 선택을 한 셈으로, 자바스크립트 생태계 성능 병목의 상당 부분이
이제 "자바스크립트로 짠 툴체인 자체"로 지목되고 있다는 신호로 읽힙니다.

### 실무 영향

- React Compiler 러스트 포트는 아직 실험 단계이므로 프로덕션에 바로 투입하기보다는, Turbopack ·
  Next.js 조합을 쓰는 팀이라면 별도 브랜치에서 컴파일 시간 개선폭을 먼저 측정해볼 만합니다.
- 신규 툴체인을 고를 때 "러스트 기반인가"가 더 이상 부가 정보가 아니라 장기 유지보수·성능 로드맵을
  가늠하는 기준으로 자리잡고 있다는 점을 팀 내부 기술 선택 기준에 반영할 만합니다.

## Bun 1.4.1／1.4.2 — Zig 런타임도 성능 경쟁에 가세

러스트 진영과 별개로, Zig 로 작성된 런타임 **Bun** 도 9월 4일 1.4.1을 내놓으며 성능 경쟁에 불을
지폈습니다. `Bun.serve()` 에 HTTP/2 지원이 추가돼 "Hello World" GET 벤치마크가 초당 291,512 요청으로,
Node.js(55,619 요청/초) 대비 6.8배 처리량을 기록했습니다. `buf.writeFloatLE()` 같은 Buffer 연산은
2.85ns 에서 0.31ns 로 9.2배, `AsyncLocalStorage` 는 `await` 마다의 할당을 없애 약 2배, 대용량 객체의
`Bun.inspect` 는 140ms 에서 3.2ms 로 43배 빨라졌습니다
([Bun v1.4.1 릴리스 노트](https://bun.com/blog/release-notes/bun-v1.4.1)).

빌드 쪽에서는 동적 `import()` 에도 트리 셰이킹이 적용돼 Zod 번들 크기가 375.3KB 에서 77.3KB 로
79% 줄었고, `--splitting` 청크 수는 219개에서 151개로 감소했습니다. 컴파일 실행파일의 바이트코드
크기는 원본 대비 9배에서 3배로 개선돼, Claude Code 를 컴파일 실행파일로 설치할 때 용량이 376MB 에서
207MB 로 45% 줄었습니다. `bun install --offline` 과 워크스페이스용 자체 포함 `node_modules` 도 이번에
추가됐고, 이번 릴리스는 202개 이슈를 수정했습니다
([Bun v1.4.1 릴리스 노트](https://bun.com/blog/release-notes/bun-v1.4.1)).

다음날인 9월 5일 나온 1.4.2는 1.4.1의 회귀 두 건 — `bun build` 가 같은 블록 안의 `var` 를 `let` 으로
잘못 리네임해 Elysia 앱을 깨뜨리던 버그, `AsyncLocalStorage` 의 `exit()`·중첩 `run()` 이 바깥 스토어를
계속 참조하던 메모리 누수 — 를 하루 만에 패치했습니다. 이와 함께 `worker_threads` 의 `'online'` 이벤트
순서를 고쳐 `@discordjs/ws` 의 행(hang) 문제를 해결했고, 약 350개의 업스트림 WebKit 커밋을 끌어와
`Intl`·타입드 배열 정확성 문제와 `Date` 객체 생성 비용도 함께 개선했습니다
([Bun v1.4.2 릴리스 노트](https://bun.com/blog/release-notes/bun-v1.4.2)).

### 실무 영향

- HTTP/2·Buffer·AsyncLocalStorage 성능에 민감한 서버 워크로드를 Bun 으로 운영 중이라면 1.4.1 업그레이드
  효과가 클 수 있지만, Elysia 나 `AsyncLocalStorage` 를 쓰는 프로젝트는 1.4.1을 건너뛰고 바로 1.4.2로
  올리는 편이 안전합니다.
- 컴파일 실행파일로 CLI 도구를 배포하는 팀은 바이트코드 경량화만으로도 배포 이미지·아티팩트 용량을
  눈에 띄게 줄일 수 있습니다.
