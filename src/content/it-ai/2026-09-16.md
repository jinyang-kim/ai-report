## 보안 — SHA-1 HTTPS 완전 차단 시행, AI 코드 스캔은 API 로 관리

GitHub 가 4월에 예고했던 일정대로 9월 15일 **SHA-1 in HTTPS 를 완전히 차단**했습니다. github.com 과
GitHub Enterprise Cloud(Data Residency 포함)의 HTTPS 연결에서 SHA-1 기반 암호를 더 이상 지원하지
않으며, 온프레미스로 운영하는 GitHub Enterprise Server 는 영향을 받지 않습니다
([GitHub Changelog](https://github.blog/changelog/2026-09-15-sha-1-in-https-on-github-sunset/)).

구형 브라우저나 오래된 Git 클라이언트를 쓰는 경우 접속이 끊길 수 있어, GitHub 는 최신 브라우저와
Git 버전을 쓰도록 권고하며 `github.dev` 에서 이미 SHA-1 이 꺼진 상태로 접속 테스트가 가능하다고
안내했습니다
([GitHub Changelog](https://github.blog/changelog/2026-09-15-sha-1-in-https-on-github-sunset/)).

같은 주 9월 10일에는 **AI Scan REST API** 가 퍼블릭 프리뷰로 나왔습니다. 코드 스캐닝의 AI 기반 PR
스캔 활성화 여부를 UI 클릭 없이 조직(`/orgs/{org}/code-scanning/ai-scan`)·저장소
(`/repos/{owner}/{repo}/code-scanning/ai-scan`) 단위로 읽고 바꿀 수 있는 엔드포인트로, GitHub Advanced
Security 구독이 있는 github.com 저장소에 우선 적용됩니다(Enterprise Server 미지원)
([GitHub Changelog](https://github.blog/changelog/2026-09-10-ai-scan-for-pull-request-apis-in-public-preview/)).

### 실무 영향

- 오래된 CI 러너 이미지나 사내 프록시를 거쳐 github.com 에 접속하는 파이프라인이 있다면, SHA-1
  차단으로 인증서 협상이 실패하지 않는지 먼저 점검할 필요가 있습니다.
- 여러 저장소에 AI Scan 을 일괄 켜야 하는 보안팀은 UI 대신 새 API 로 Terraform·스크립트에 편입시켜
  두면 신규 저장소가 생길 때마다 수동으로 설정할 필요가 없어집니다.

## GitHub Actions — 캐시 접근을 4단계로 세분화하는 cache-mode GA

GitHub Actions 캐시 접근을 최소 권한 원칙으로 통제하는 **cache-mode** 가 정식 출시(GA)됐습니다. 워크플로
또는 잡 단위로 `read`(복원만) · `write`(복원+저장) · `write-only`(저장만, 복원 불가) · `none`(전면 차단)
네 단계를 지정할 수 있습니다. 기본값은 PR 같은 신뢰되지 않은 이벤트는 `read`, push 같은 신뢰된
이벤트는 `write` 입니다
([GitHub Changelog](https://github.blog/changelog/2026-09-10-control-github-actions-cache-access-with-cache-mode/)).

> "The selected mode is enforced by the cache service and carries through reusable workflows, where a called workflow cannot receive more cache access than its caller granted."

잡 단위 설정이 워크플로 단위 설정을 덮어쓰고, 재사용 워크플로를 호출해도 호출자가 준 권한보다
넓은 캐시 접근을 받을 수 없도록 강제됩니다. 캐시 포이즈닝 — 오염된 캐시를 심어 이후 빌드에
악성 산출물을 주입하는 공격 — 표면을 줄이기 위한 조치입니다
([GitHub Changelog](https://github.blog/changelog/2026-09-10-control-github-actions-cache-access-with-cache-mode/)).

### 실무 영향

- 포크에서 오는 PR 워크플로처럼 신뢰도가 낮은 트리거에는 `read` 또는 `none` 을 명시해, 외부 기여자가
  캐시에 쓰기 접근을 얻지 못하도록 워크플로 정의를 다시 점검할 만합니다.
- 빌드 아티팩트만 캐시에 쌓아두고 이후 잡에서 읽지 않는 파이프라인이라면 `write-only` 로 좁혀 불필요한
  복원 시도를 줄일 수 있습니다.

## GitHub Copilot 코드 리뷰 — 커밋 자동 해결 + 앙상블 리뷰로 정확도 개선

GitHub Copilot 코드 리뷰가 9월 11일 두 가지 기능을 추가했습니다. 첫째, 리뷰 코멘트를 해결하는
후속 커밋을 푸시하면 재리뷰 시 해당 코멘트가 **자동으로 해결(resolve)** 처리됩니다. 둘째, autofix
제안을 적용할 때 코드 변경 내용에 맞춘 **커밋 메시지를 자동 생성**해 일반적인 기본 메시지를 대체합니다
([GitHub Changelog](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/)).

분석 품질도 개선됐습니다. 리뷰 에이전트가 Copilot SDK 의 셸 도구 전체를 활용해 빌드 명령·테스트·
스크립트로 코드를 직접 검증할 수 있게 됐고, Lite 등급에서는 여러 에이전트의 리뷰 결과를 하나로
합치는 **앙상블 리뷰**를 도입했습니다. 테스트 결과 고심각도 지적이 47%, 중간 심각도가 31%, 경미한
지적이 11% 늘었고 비용은 약 8% 줄었으며, 사소한 지적의 노출은 줄어 개발자 피드백도 더 긍정적이었습니다
([GitHub Changelog](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/)).

### 실무 영향

- 리뷰 코멘트를 수동으로 닫아온 팀이라면 자동 해결 덕분에 재리뷰 루프에서 이미 고친 지적을 다시
  확인하는 시간을 줄일 수 있습니다.
- 빌드·테스트 실행 기반 검증이 추가된 만큼, 리뷰가 느려지거나 CI 리소스를 더 쓰는지 도입 초기에는
  실행 시간과 비용을 함께 모니터링하는 편이 안전합니다.
