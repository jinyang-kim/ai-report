## GitHub Actions 러너 — Ubuntu 26.04 GA 와 22.04 폐기가 같은 날 맞물리다

GitHub Actions 의 **Ubuntu 26.04** 러너 이미지가 9월 17일 프리뷰를 졸업하고 x64·arm64 모두에서 정식
프로덕션 워크플로를 지원하게 됐습니다. `ubuntu-latest` 라벨은 10월 19일부터 11월 19일 사이 이 이미지로
순차 전환되며, 그전까지 현재 이미지를 유지하고 싶다면 `runs-on: ubuntu-24.04` 로 명시 고정해야 합니다
([GitHub Changelog](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration)).
반대로 새 이미지를 먼저 써보려면 `runs-on: ubuntu-26.04` 또는 `ubuntu-26.04-arm` 을 지정하면 됩니다.
GitHub 는 "마이그레이션이 시작되기 전에 `ubuntu-26.04` 로 워크플로를 테스트하라"고 명시했는데, 버전이
바뀌며 제거되거나 갱신된 패키지 때문에 빌드가 깨질 수 있기 때문입니다
([GitHub Changelog](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration)).

같은 날 반대쪽 끝에서는 **Ubuntu 22.04** 이미지의 폐기 절차가 시작됐습니다. GitHub 는 OS 계열당 최대
두 개의 GA 이미지만 유지하는 정책에 따라, 가장 최신 이미지(26.04)가 GA 되는 시점에 가장 오래된
이미지(22.04)의 폐기를 시작합니다. 완전 제거는 2027년 4월 17일이며, 그 전까지 브라운아웃(일시적
장애) 구간이 단계적으로 예정돼 있습니다
([actions/runner-images#14254](https://github.com/actions/runner-images/issues/14254)). `ubuntu-22.04` 를
명시적으로 지정한 워크플로가 있다면 `ubuntu-24.04`·`ubuntu-26.04`·`ubuntu-latest` 중 하나로 옮겨야 합니다.

### 실무 영향

- `ubuntu-latest` 를 그대로 쓰는 워크플로는 11월 19일 이후 자동으로 26.04 로 넘어갑니다. 특정 apt
  패키지 버전이나 사전 설치 도구에 의존하는 빌드 스크립트가 있다면, 마이그레이션 창이 열리기 전에
  `ubuntu-26.04` 러너로 한 번 돌려보는 편이 안전합니다.
- `ubuntu-22.04` 를 하드코딩한 워크플로·재사용 액션이 조직 내에 남아 있는지 지금 점검해두면, 2027년
  4월 브라운아웃 구간에서 급하게 대응하는 상황을 피할 수 있습니다.

## GitHub Actions 워크플로 실행 보호 GA — 'Pwn Request' 를 트리거 단계에서 차단

GitHub Actions 의 **워크플로 실행 보호(Workflow execution protections)** 기능이 9월 17일 정식
출시됐습니다. 저장소·조직·엔터프라이즈 단위로 "누가, 어떤 이벤트로 워크플로를 실행할 수 있는지"를
액터·이벤트 규칙으로 정의할 수 있고, 워크플로 파일 단위 타기팅과 영향 확인용 인사이트 대시보드,
REST API 관리 기능이 함께 제공됩니다
([GitHub Changelog](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available)).

이 기능이 정면으로 겨냥하는 것은 **'Pwn Request'** 공격입니다. `pull_request_target` 이벤트로 실행되는
워크플로는 베이스 저장소의 `GITHUB_TOKEN` 과 시크릿에 접근할 수 있는데, 포크에서 열린 PR 의
Makefile·빌드 스크립트·테스트 커맨드에 악성 코드를 심어두면 이 워크플로가 그 코드를 실행하면서
시크릿이 그대로 유출될 수 있습니다
([GitHub Docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)).

> An attacker only needs to open a pull request from a fork whose Makefile (or build script, test command, dependency, or configuration file) contains malicious commands.

GitHub 는 11월 2일부터 퍼블릭 저장소에서 액션 이벤트 정책으로 명시 허용하지 않는 한
`pull_request_target` 을 기본 차단하기로 했습니다. 그전까지는 '평가(shadow) 모드'로 동작해 Insights
화면에서 이 규칙이 켜졌을 때 어떤 워크플로가 영향을 받는지 먼저 확인할 수 있습니다
([GitHub Changelog](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available)).

이번 GA 는 갑자기 나온 조치가 아닙니다. GitHub 는 지난 6월 18일 `actions/checkout` v7 을 GA 하면서
`pull_request_target` 워크플로가 포크의 PR 헤드·머지 커밋을 체크아웃하려 하면 자동으로 실패시키도록
바꾼 바 있습니다. 우회하려면 `allow-unsafe-pr-checkout: true` 를 명시해야 하는데, GitHub 는 이 플래그를
"코드 리뷰·정적 분석에서 눈에 잘 띄도록" 일부러 이런 이름으로 지었다고 설명했습니다
([GitHub Changelog](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/)).
6월 조치가 '체크아웃 단계'의 방어였다면, 이번 9월 조치는 그보다 앞선 '트리거 단계'에서부터 막는
정책으로, 방어선이 한 단계 앞으로 이동한 셈입니다.

### 실무 영향

- 퍼블릭 저장소를 운영하는 조직은 11월 2일 기본 차단이 적용되기 전에 Insights 화면에서 자신의
  `pull_request_target` 사용 워크플로가 실제로 필요한 것인지, 정책으로 명시 허용해야 하는지 먼저
  점검할 만합니다.
- 여러 저장소를 관리하는 보안팀이라면 이번 REST API 관리 기능으로 조직 전체에 실행 보호 규칙을
  일괄 적용하고, 저장소별 예외만 화이트리스트로 관리하는 방식이 개별 저장소 설정보다 유지보수하기
  쉽습니다.
